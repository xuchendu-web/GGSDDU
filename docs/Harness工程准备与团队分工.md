# Harness 工程准备与团队分工（宽基分析层 v1.0）

> 对应《宽基分析层-需求与框架》的 M0-M6 实施路线。本文档回答三个问题：Harness 系统要做哪些准备、需要调用哪些资源、团队怎么分配。
>
> 架构总原则（Agent = Model + Harness）：Model 决定智能上限，Harness 决定产出下限。本系统的可靠性（数字准确、可溯源、可审计）全部由 Harness 保证，大模型只负责组织语言与逻辑解释。

---

## 一、Harness 系统准备清单（10 个子系统）

| # | 子系统 | 要准备什么 | 关键设计决策 | 服务的功能模块 | 优先级 |
|---|---|---|---|---|---|
| H1 | 数据适配层 | 统一数据访问接口（DataProvider 抽象）+ Wind/聚源/恒生/客户数仓各一个适配器实现；字段映射配置表；取数缓存；**数据快照存档**（每次分析冻结一份带编号的数据切片） | 适配器接口先于一切业务代码定义；快照是溯源与证据包的基石，必须从第一天做 | 全部 | P0 |
| H2 | 信号计算引擎 | 规则标定表 v1 全部指标的确定性计算：估值分位、ERP、跟踪误差、流动性评级、折溢价、拥挤度、资金流；计算结果带规则版本号入库 | 纯 Python 确定性计算，可单测、可复算；LLM 禁止参与任何数值产出 | F1-F4、F9 | P0 |
| H3 | 工具层封装 | 把 F1-F10 每个能力封装为带 schema 的工具（输入参数、输出结构、异常约定），注册到工具注册表 | 工具 schema 就是前后端与编排层的接口契约，先冻结契约再并行开发 | 全部 | P0 |
| H4 | 编排引擎 | 意图识别与参数提取 → 分类路由（查映射表）→ 工具调用编排（并行采数、串行生成）→ 校验 → 渲染；条件分支、重试（≤3 次）、降级策略（数据缺失标注继续 / 校验失败转人工） | 沿用券商开发方案的 LangGraph 状态机骨架，但从"固定流水线"改造为"工具集调度"，为对话层复用 | 全部 | P0 |
| H5 | 上下文工程 | 三类规则文档 → 系统提示词固定部分；TCRII 模板 → Jinja2 模板文件（变量占位符 + 填充规则 + 完整性检查，未填变量禁止发送）；报告四档篇幅路由（深报告/决策卡/快评/筛选） | 模板与规则文档进 Git 版本管理，带版本号，热更新不停服 | F7 | P0 |
| H6 | 校验器 | 三层校验：①格式校验（来源标注、≥3 条反向风险、禁用词、15 条易错点）②**数值比对**（报告中每个数字 vs 数据快照自动比对，不一致强制重写）③降级出口（3 次重写失败转人工复核队列） | 数值比对是机构可信度的生命线，比正则格式检查优先级更高 | F10 | P0 |
| H7 | 评分与约束引擎 | 产品质量分/时机分/拥挤度分/组合适配分的加权计算；场景权重配置（配置/交易/替换型）；客户约束过滤（白名单、集中度、费率上限）；回测框架（评分规则历史有效性验证） | 权重与约束全部配置化，客户可自维护；回测报告作为售前材料 | F5 | P0（回测 P1 前置） |
| H8 | 记忆与会话系统 | 短期：会话状态（当前指数、组合、建仓金额、已应用筛选），支撑多轮追问与参数改写重算；长期：用户偏好（常看指数、默认场景、订阅项） | 会话状态是对话层"顺手"的关键，schema 与工具层联合设计 | F8 | P1 |
| H9 | 交付渲染层 | 决策卡前端（含下钻交互）、对话 UI、监控中心；报告渲染 MD→PDF/HTML/Excel 底稿（按输出格式规范表：蓝底表头、风险表红底、数值精度规则） | 决策卡每个结论块携带"下钻锚点"（规则条目 + 快照字段引用），前端只做展示不做计算 | F7 F8 F9 | P0（决策卡）P1（对话/监控） |
| H10 | 审计与运维 | 证据包归档（快照+评分明细+规则版本+生成日志）；全程审计日志；配置热更新；模型调用监控（延迟/成本/失败率）；K8s 部署与告警 | 证据包目录结构与客户合规复核流程对齐，交付时作为标准输出物 | 全部 | P0（留痕）P1（运维完善） |

## 二、需要调用的资源清单

| 类别 | 资源 | 用途 | 获取方式 / 责任方 | 前置风险 |
|---|---|---|---|---|
| 数据-行情估值 | 客户数据终端 API（Wind/聚源/恒生任一） | 行情、估值、产品、资金全部动态数据 | **客户提供账号与权限**，售前即确认字段清单 | 字段权限不足是最大启动风险，M0 首项任务 |
| 数据-指数 | 中证指数公司成分/编制规则数据 | 指数结构、行业市值分布、调样 | 客户终端转接或指数公司接口 | 调样日更新时效 |
| 数据-公告 | 基金定期报告、上市公告 | 费率、做市商、复制方式、机构持有人占比 | 公开渠道 + 解析管道 | 半结构化解析工作量 |
| 数据-宏观 | GDP/PMI/CPI/社融/国债收益率/DR007 | 时机面板宏观四维 | 客户终端 + 联网搜索（政策事件） | 联网搜索需内网代理审计 |
| 数据-客户内部 | 组合持仓、白名单、风控约束参数 | 组合关联（F6）、约束过滤（F5） | **客户数仓接口或文件对接**，M4 前到位 | 各客户格式异构，靠适配器消化 |
| 数据-因子 | 风格因子暴露数据（Barra 类或自算简化因子） | 组合暴露变化测算 | 客户已购因子库优先；否则用规模/价值/动量简化因子自算 | 自算因子需业务认可口径 |
| 模型-大模型 | 私有化部署（DeepSeek-R1/Qwen3 类）或客户指定模型网关 | 报告生成、意图识别、对话 | 客户内网 GPU 集群 / 客户模型平台 | 私有化模型能力弱于旗舰 API，提示词需按实际模型调优 |
| 模型-辅助 | Embedding 模型 | 报告库 RAG（对话引用历史报告） | 随大模型一并部署 | P1 阶段才需要 |
| 业务资产 | 券商交付的八类模板、三类规则文档、参数表、预警规则表 | H5 H6 H7 的内容底料 | 已有（本仓库 5 份文档），需人工校对 AI 生成部分的错漏 | 两份文档带 AI 生成标记，表格有残缺 |
| 业务资产 | 阈值标定评审（业务专家/种子客户投研） | 规则标定表 v1 签字定版；新增指标（ERP/资金流/宽基拥挤度）背书 | **总工程师组织评审会**，M0 完成 | 无背书则全部产出缺公信力 |
| 业务资产 | 黄金样例标准答案（沪深300/科创50/中证500 人工报告） | 回归测试基准、盲测对照 | 业务专家撰写或客户提供存量研报 | 需在 M1 前就绪 |
| 基础设施 | PostgreSQL（映射表/参数表/快照索引）、Redis（缓存/会话）、对象存储（快照/证据包/报告归档）、K8s | 运行环境 | 客户内网环境，运维协调 | 客户环境审批周期，尽早申请 |
| 基础设施 | 邮件网关 / 门户看板接口 | 监控推送、快评触达 | 客户 IT 对接 | P1 阶段到位即可 |

## 三、团队分配（总工程师视角）

### 3.1 角色与职责

| 角色 | 人数 | 负责子系统 | 核心交付 | 技能要求 |

| 后端工程 | 1 | H3 H4 H9(渲染) H10 | 工具注册表、编排引擎、报告渲染管道、监控服务、证据包归档 | Python、LangGraph、异步、K8s |

### 3.3 关键路径与并行策略

```
关键路径：H1 适配器 → H2 信号引擎 → H4 编排 → M1 报告打穿 → M2 回测 → M3 决策卡 → M6 POC
```

| 并行策略 | 说明 |
|---|---|
| 契约先行 | 总工程师在 M0 第一件事：冻结工具 schema 与信号数据结构。此后 LLM 工程用 mock 信号数据开发模板与校验器、前端用 mock 接口开发决策卡，不等数据层 |
| 最强的人放数据层 | 字段对齐、口径差异、数据质量是全项目最大时间黑洞（远超模型调优），数据工程配置最有终端 API 经验的人 |
| 回测与开发并行 | 量化工程在 M1 期间即启动评分回测，不等 M2 才开始；回测暴露的阈值问题反馈给标定表 v1.1 |
| 校验器与生成同人 | 提示词与校验器由同一个 LLM 工程师负责——写模板的人最清楚模型会在哪里犯错 |
| 测试从 M0 介入 | 黄金样例、数值比对脚本在 M1 前就绪，每次迭代自动回归，不做"最后集中测试" |

### 3.4 需要总工程师亲自把住的五个决策点

| 决策点 | 为什么不能下放 |
|---|---|
| 工具 schema 契约冻结 | 全团队并行开发的前提，改一次接口全员返工 |
| 阈值标定评审会 | 业务公信力问题，需要与客户投研直接对话 |
| 因子模型口径（Barra 采购 vs 简化自算） | 成本、周期、客户认可度三方权衡，影响 M4 方案 |
| 私有化模型选型与提示词适配深度 | 模型能力决定模板复杂度上限，选错返工成本极高 |
| 证据包规格与客户合规流程对齐 | "合规交给客户"商业模式成立的前提，属合同层面事项 |
