# 券商研究资源的分配与调用机制（v1.0）

> 定位：券商研究资源是本系统的"内容供应链"。工程团队负责管道，券商负责弹药——本文档定义弹药的种类、分配、系统调用方式与治理流程。
>
> 总原则：**券商产出"判断标准与研究内容"，系统负责"工程化调用与留痕"**。凡是会随市场变化的判断，绝不硬编码进系统，全部走"券商可维护的配置/内容通道"。

---

## 一、券商研究资源盘点（四类资产）

| 类别 | 具体资源 | 现状 | 变化频率 | 系统内的形态 |
|---|---|---|---|---|
| A. 静态知识资产 | 八类 ETF 提示词模板、三类规则文档（总规则/15 条易错/偏好）、七段式报告框架 | 已交付（本仓库），需校对 AI 生成部分 | 低（半年级） | 版本化模板文件 + 系统提示词 |
| B. 参数与标定资产 | 8 张参数表、分类映射表（前 200 只）、预警阈值表、可比指数清单、估值中枢参考 | 部分交付，宽基参数表待填 | 中（季度 Review + 事件触发） | 数据库配置表，热更新 |
| C. 动态研究产出 | 定期研报（宏观/策略/行业景气）、估值观点、风格判断、事件点评 | 券商日常产出，未接入 | 高（日/周） | 研报库 + RAG 检索源 |
| D. 专家人力 | 研究员评审（阈值标定）、盲测打分、人工复核节点、新 ETF 分类标注 | 按需协调 | 事件驱动 | 复核队列 + 评审会机制 |

四类资产的价值密度和调用方式完全不同，必须分开设计通道，不能混为"给券商提需求"一个筐。

## 二、分配：券商侧与工程侧的责任切分

| 事项 | 券商研究侧 | 工程侧 | 交接物 |
|---|---|---|---|
| 分类体系与映射 | 定标准（宽基/行业/主题边界、行业分类口径）、标注前 200 只、新 ETF 增量标注 | 建路由表、自动预分类（LLM 临时分类→挂起待确认） | 分类映射表（Excel→DB） |
| 判断阈值 | 给出并背书全部阈值（估值分位/流动性/费率分档…）、季度 Review | 阈值→规则引擎配置、版本管理、触发监控 | 规则标定表（签字版） |
| 参数表 | 填写并维护 8 张参数表（可比清单、驱动变量、估值中枢） | 参数→配置表、字段完整性校验、变更审计 | 参数表（逐行填写，禁"视情况而定"） |
| 提示词模板 | 审定业务表述、判断逻辑、报告结构 | 变量占位、填充引擎、版本管理 | TCRII 模板（业务定稿→Jinja2） |
| 动态观点 | 日常研报按约定格式/频率入库 | RAG 管道、时效控制、引用标注 | 研报文件（带元数据） |
| 质量验收 | 黄金样例撰写、盲测打分（≥80 分标准） | 回归自动化、盲测组织与统计 | 盲测评分表 |
| 人工复核 | 复核队列值班响应（分类确认、校验失败报告） | 队列系统、SLA 监控、超时升级 | 复核工单 |

**分配的核心逻辑**：券商研究员的时间是最贵的资源，只花在三件事上——**定标准（一次性）、维护参数（季度）、处理例外（事件驱动）**。日常报告生成完全不占用研究员时间，这是系统对券商的价值承诺，也是内容合作可持续的前提。

## 三、调用：系统消费券商资源的四条技术通道

### 通道 1：配置化调用（B 类资产，主通道）

```
券商填表 → 导入校验（完整性/格式/禁模糊表述）→ 配置库（带版本号）→ 信号引擎/路由/评分引擎实时读取
```

| 设计要点 | 说明 |
|---|---|
| 热更新 | 参数变更审核后即时生效，无需发版（沿用券商开发方案的配置热更新机制） |
| 版本快照 | 每次分析记录所用配置版本，证据包可回放"当时用的是哪套阈值" |
| 导入校验 | 拒绝"视情况而定"类模糊值；字段缺失自动生成待办退回券商 |
| 变更审计 | 谁改的、何时改的、改前改后值，全程留痕 |

### 通道 2：RAG 检索调用（C 类资产，观点通道）

```
券商研报入库（带元数据：日期/作者/品类/观点方向）→ 切片向量化 → 生成报告时按品类+时效检索 → 观点注入提示词上下文 → 输出带【来源：XX证券研报，日期】
```

| 设计要点 | 说明 |
|---|---|
| 时效衰减 | 宏观/策略观点默认只取近 30 天，行业景气取近 90 天，过期自动降权不引用 |
| 观点与数据分离 | 券商观点作为"研究判断"注入，与信号引擎的"计算事实"在报告中分层表述，不允许观点覆盖数据 |
| 冲突处理 | 券商观点与信号引擎结论冲突时（如券商看多但估值分位 >90%），报告须并列呈现并标注分歧，不做静默取舍 |
| 引用留痕 | 每次引用记录研报 ID，支持券商追溯自己观点的使用情况 |

### 通道 3：人工节点调用（D 类资产，例外通道）

| 触发场景 | 调用方式 | SLA 建议 |
|---|---|---|
| 新 ETF 不在映射表 | LLM 临时分类 → 复核队列 → 研究员确认 → 写回映射表 | 下一交易日内 |
| 报告三次校验失败 | 连同已生成内容推送复核队列 | 当日 |
| 数据缺失率 >30% | 标记"建议人工复核"，附缺失清单 | 当日 |
| 阈值触发争议（客户质疑判断） | 升级至评审通道，输出书面口径说明 | 按事件 |

队列系统需给券商研究员一个极轻的操作界面（确认/修改/驳回三键），研究员单次处理成本控制在分钟级，否则响应会劣化。

### 通道 4：评审会调用（D 类资产，治理通道）

| 评审会 | 时点 | 输入 | 输出 |
|---|---|---|---|
| 阈值标定评审 | M0 + 此后每季度 | 标定表草案 + 回测数据 | 签字版规则标定表 vN |
| 黄金样例评审 | M1 前 | 三只指数 AI 报告 vs 人工报告 | 标准答案基准集 |
| 盲测验收 | M6 及每次大版本 | 10 只测试 ETF 报告 | 评分表（≥80 分放行） |
| 参数 Review | 每季度 | 参数表现况 + 失效预警（如估值中枢被持续突破） | 参数表 vN+1 |

## 四、治理：让内容供应链可持续的三件事

### 4.1 更新责任矩阵（对齐券商开发方案的运维规范并加严）

| 维护项 | 频率 | 券商动作 | 系统动作 |
|---|---|---|---|
| 分类映射表 | 新 ETF 上市触发 | 增量标注 | 自动检测新上市 ETF 生成待办 |
| 参数表/阈值 | 季度 + 事件触发 | Review 并提交变更 | 失效监控（阈值被市场持续突破时主动预警券商） |
| 提示词模板 | 半年 + 盲测反馈触发 | 审定业务表述 | A/B 对比新旧模板生成质量 |
| 研报入库 | 日/周 | 按格式推送 | 入库校验 + 时效管理 |

关键设计：**系统主动监控内容失效并反向催办券商**（如"沪深300 估值中枢 PE 11-16 倍已连续 60 日被突破，请 Review"），而不是被动等券商想起来更新。这是配置驱动系统防腐化的核心机制。

### 4.2 版本与追责

- 全部 B 类资产带版本号；任何一份输出报告可回放到"当时的模板版本 + 参数版本 + 阈值版本 + 研报引用清单"；
- 客户质疑某个判断时，责任可清晰切分：判断标准问题→券商口径，计算错误→工程问题，数据错误→数据源问题。这个切分能力对三方合作关系至关重要。

### 4.3 商业与风险考量

| 事项 | 建议 |
|---|---|
| 内容授权模式 | 券商内容（模板+参数+观点）作为可订阅的内容服务计价，与系统license 分开——券商由"一次性交付方"变为"持续内容供应商"，利益绑定后维护积极性才有保障 |
| 单一券商依赖 | 内容层与管道层严格解耦（本来就是配置化的），预留多内容源架构：未来可接入第二家券商或客户自有研究团队的参数表，同一管道多套内容 |
| 客户自有研究优先 | 公募/理财子客户自己有研究部——支持客户用自有观点/阈值覆盖券商默认值（配置层面的 override 机制），券商内容退为"出厂默认值"。这既化解客户"凭什么用你家券商观点"的抵触，也降低单一依赖风险 |
| 观点合规边界 | 券商研报仅供客户机构内部使用，入库范围与转授权条款写入三方协议 |

## 五、按里程碑的券商资源需求排期

| 里程碑 | 需要券商投入什么 | 工程侧提前准备什么 |
|---|---|---|
| M0 | 标定评审会（研究员出席）、宽基参数表填写、映射表前 200 只标注 | 标定表草案、填表模板与导入校验工具 |
| M1 | 黄金样例标准答案（3 只指数）、模板业务表述审定 | AI 报告初稿供对照、评审材料 |
| M2 | 评分权重与回测结果确认 | 回测报告 |
| M3 | 8 只宽基参数补全 | 参数缺口清单 |
| M4 | （客户侧为主，券商备询） | — |
| M5 | 研报入库通道联调、复核队列值班机制确定 | RAG 管道、队列界面 |
| M6 | 盲测打分（10 只 ETF） | 盲测组织与统计 |
