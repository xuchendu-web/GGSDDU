# 券商研究所课题委托合作模式（v1.0）

> 回答的问题：怎么让券商研究所帮我一起实现系统开发？课题委托能覆盖什么、不能覆盖什么、怎么设计课题包、怎么谈、怎么管。
>
> 一句话结论：**课题委托是获取业务知识资产的正确工具，但它交付的是文档/表格/标准/评审意见，不是代码。工程必须留在自己团队。** 仓库中《券商课题-ETF.doc》就是这一模式的现成范本（模块化任务书 + 权重 + 交付物验收标准），照此升级即可。

---

## 一、先校准预期：研究所能做什么、不能做什么

| 团队 | 能承接的课题内容 | 不能指望的 |
|---|---|---|
| 行业/策略分析师 | 分类体系、判断阈值、参数表填写、提示词业务表述审定、黄金样例报告撰写、盲测打分、季度参数 Review、动态观点供给 | 任何代码；数据管道；系统设计。分析师的产出物是 Word/Excel |
| 金融工程组（金工） | **量化方法论**：估值分位/跟踪误差/拥挤度的计算口径定义、评分权重建议、回测方案设计与结果复核、因子口径评审 | 生产级代码。金工可以给 Python 原型或公式文档，但原型必须由你的量化工程师重写为生产代码 |
| 研究所管理层（所长/首席） | 课题立项、人力承诺、署名背书、对外联合发布 | 日常执行细节 |
| 研究所公司层（合规/法务） | 内容授权、对外输出合规边界 | — |

**误区警示**：如果合同里写"券商负责开发 XX 模块"，最终会得到一份"开发方案文档"而不是可运行的模块——仓库里那份《ETF分析SKILL 开发方案.doc》（AI 生成、表格残缺）就是这种错配的产物。研究所的组织能力边界就是"研究交付物"。

## 二、课题包设计：把业务侧需求全部课题化

把《券商研究资源分配与调用机制》中的券商投入清单，改写成研究所熟悉的课题任务书格式（模块 + 权重 + 验收标准），拆成一个总课题、四个子课题：

### 总课题：《ETF 智能投研系统业务标准体系建设》

| 子课题 | 交付物 | 验收标准（写入合同） | 对口团队 |
|---|---|---|---|
| 子课题 A：分类与标定 | ①全市场前 200 只 ETF 三级分类映射表 ②宽基/行业/主题等 8 张参数表 ③判断规则标定表（全部阈值签字背书） | 每个字段有具体数值/判断标准/数据来源，零"视情况而定"；映射表抽检准确率 100%；标定表经评审会签字 | 各行业分析师 + 金工 |
| 子课题 B：方法论与模板 | ①八类 ETF 分析模板业务定稿 ②三类规则文档修订版（校对现有 AI 生成稿的错漏） ③新增指标（ERP/资金流/宽基拥挤度）计算口径与阈值论证报告 | 模板经首席签发；新增指标附历史数据论证（非拍脑袋） | 策略分析师 + 金工 |
| 子课题 C：质量基准 | ①黄金样例标准报告（沪深300/科创50/中证500 人工撰写） ②盲测评分（每次大版本 10 只 ETF，评分表） | 黄金样例达到该所对外研报质量；盲测按约定五维评分（数据准确 30%/深度 25%/结构 15%/风险 15%/可读 15%） | 指定资深分析师 |
| 子课题 D：持续内容服务（续约制） | ①季度参数 Review 与更新 ②研报按格式入库（RAG 通道） ③复核队列值班响应（分类确认/争议口径，SLA：下一交易日） | 每季度交付更新记录；催办工单响应达标率 ≥95% | 轮值分析师 + 助理 |

**设计要点**：A/B/C 是一次性课题（对应系统建设期 M0-M6），D 是**年度续约的内容订阅**——这是防止"课题交付完就失联"的关键结构。研究所对一次性课题的交付质量取决于后面还有没有续约收入。

## 三、商务谈判要点（合同里必须钉死的五件事）

| # | 条款 | 为什么关键 |
|---|---|---|
| 1 | **知识产权授权** | 现有材料是为单次课题写的。你要把系统卖给多家公募/理财子，模板、参数表、阈值体系必须取得**可商业化再许可**的授权（买断或按装机分成）。不谈妥这条，系统每卖一家都是侵权风险。这是整个合作中最容易被忽略、代价最大的一条 |
| 2 | **人力承诺具体到人** | 课题合同写"研究所安排人员支持"等于没写。要求写明：课题负责人（首席/资深分析师姓名）、各子课题对口分析师、金工对口人，及其最低投入承诺。分析师流动时研究所有义务指定同级别继任者 |
| 3 | **验收标准量化** | 直接复用课题任务书的权重打分模式，每个交付物附验收表；分期付款与验收挂钩（如 A/B/C 各 30%，验收后付） |
| 4 | **维护 SLA 与续约** | 子课题 D 单独计价、按年续约；写明季度 Review 义务、复核响应 SLA、阈值失效催办的响应义务 |
| 5 | **署名与对外口径** | 允许研究所在系统输出中署名（【来源：XX证券研究所】）既是卖点也是他们的激励；同时约定客户机构内部使用范围，避免触碰研报对外分发的合规红线 |

**付费模式现实说明**：你作为系统商委托研究所，走的是**直接的研究咨询服务合同**（研究所有对外提供咨询服务的资质通道）。另一条可叠加的路径：你的公募客户本来就通过分仓佣金采购该券商研究服务——可以设计三方结构，让客户指定其合作券商作为系统的"内容供应方"，你只做管道。这条路能大幅降低你的内容采购成本，但要接受"每个客户可能指定不同券商"的多内容源现实（架构上已预留）。

## 四、激励设计：让分析师真的上心

分析师的时间被排名（新财富等）、路演、内部服务瓜分，课题在他们的优先级里默认垫底。可用的抓手：

| 抓手 | 说明 |
|---|---|
| 钱给到组 | 课题费在研究所内部要能分到执行团队（谈判时向所长确认分配机制），否则执行层没动力 |
| 署名与成果 | 系统输出带研究所署名；联合发布《ETF 智能投研白皮书》——分析师可将其计入个人研究成果 |
| 数字化转型 KPI | 券商研究所普遍背"研究数字化/AI 化"的考核指标，你的课题正好是他们的成果案例，立项时主动往这个框架里放 |
| 反向价值 | 系统建成后免费给研究所内部使用（生成初稿提效），让他们成为用户而不只是供应商——用过的人才会持续维护参数 |
| 排他窗口 | 给首家合作研究所一段排他期或"首发合作方"名义，换取更高投入优先级 |

## 五、运行管理机制

| 机制 | 安排 |
|---|---|
| 双周课题例会 | 你方总工程师 + 研究所课题负责人；议程固定：交付物进度、待办催办、争议口径裁决 |
| 交付物直进系统 | 分析师填的表通过导入校验工具直接入库（拒绝模糊值自动退回），避免"Word 传来传去"的版本失控 |
| 里程碑评审会 | M0 标定评审、M1 黄金样例评审、M6 盲测——研究所出人出章，对应子课题验收节点 |
| 催办看板 | 系统自动生成的内容失效待办（阈值被突破、新 ETF 待分类）同步到研究所，响应纳入 D 课题 SLA 考核 |
| 烂尾预案 | 若研究所交付质量持续不达标：分期付款止付 + 内容层解耦架构保证可切换第二家研究所或客户自有研究团队，管道不受影响 |

## 六、给你的行动清单

1. 把本文件第二节的课题包改写成正式课题任务书（格式直接套用仓库《券商课题-ETF.doc》：背景 + 技术前提 + 模块 + 权重 + 交付物要求），作为谈判文本；
2. 约研究所所长/首席谈立项，开场先谈第四节的激励框架（数字化 KPI + 署名 + 续约收入），再谈交付义务；
3. 合同评审死守第三节五条，**尤其第 1 条 IP 再许可**——这条决定你的系统能不能合法地卖给第二家客户;
4. 首次交付验收用导入校验工具执行（零模糊值原则），第一次就把标准立住；
5. 同步启动自己团队的 M0（工具契约、数据适配器）——课题谈判与工程启动并行，互不等待。
